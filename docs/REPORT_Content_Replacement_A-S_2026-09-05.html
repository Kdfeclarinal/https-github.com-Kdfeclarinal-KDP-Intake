Executive summary

We delivered a server-authoritative TRUE replacement flow for Content files. The uploadContentFileToReviewStudio Edge Function now reuses the existing Manuscript Review and Cover Review (no new RS project/review), uploads the new file into the SAME review, persists the new book_files row with staged with is_latest=false, atomically promotes it while marking the old row is_latest=false, and only then DELETEs the old ReviewStudio file via DELETE /reviews/{review_id}/files/{review_file_id}. The final authoritative state exposes at most one current manuscript and at most one current cover.

The loader (loadEmployeePage) was updated to filter book_files to is_latest = true, so superseded rows become invisible to the employee UI without being hard-deleted (a reconciliation job, out of scope here, is responsible for the hard delete).

The browser never sees RS credentials, never sends RS review_id / file_id, and never picks which RS file to delete. Server resolves all RS identifiers from the trusted book_files row.

Answers A–S

A. Reuse Manuscript Review + Cover Review, not new project/review. The orchestrator reads reviewstudio_review_id and reviewstudio_file_id from the trusted book_files row and posts the new file to POST /reviews/{review_id}/files with the same review_id. No new RS project or review is created.

B. Single POST endpoint, no PUT. The new file is created via POST /reviews/{review_id}/files with the documented JSON body {name, review_file_url, source: "file", order}. There is no PUT overwrite call. The old file is removed only via DELETE.

C. No RS versioning. The replacement is not modeled as a version chain. The new file has its own review_file_id, the old one is deleted. The new book_files row carries metadata.replaces_review_file_id and metadata.replaces_book_file_id for audit traceability but the UI and the loader see only the latest row per (book_id, section_key).

D. No /remote/version endpoint used. Only POST /reviews/{review_id}/files and DELETE /reviews/{review_id}/files/{review_file_id} are called. Unit scenario 16 asserts no other endpoint is invoked.

E. Do not call response.json() on a 204. The DELETE handler awaits the raw response and reads res.status / res.ok only — no body parse. Unit scenario 8 asserts the 204 empty-body path does not crash.

F. No automatic retry of DELETE. On 5xx or network error the orchestrator sets cleanup_pending in the success result and returns. The orchestrator never re-attempts the DELETE. Scenarios 9 and 17 assert this.

G. No delete_all_versions=true. Each old file is deleted independently via the per-file DELETE endpoint. The orchestrator does not pass any version-chain query parameter.

H. Browser never sends RS IDs as authority. The Edge Function reads reviewstudio_review_id and reviewstudio_file_id from the trusted book_files row, never from the request body or query string. Unit scenario 10 (server-determined IDs) and scenario 12 (orchestrator never sends these IDs in the request) assert this end-to-end. The browser code never references these fields.

I. Server-side validation reuses the existing upload guards. The replacement path in uploadContentFileToReviewStudio_reviewstudio_flow.ts applies the same checks as the first-upload path: scoped access_token, book_id ownership, employee may modify Content, file_type ∈ {manuscript, cover}, section_key ∈ {content.manuscript, content.cover}, current workflow state permits upload. The new _replaceOrchestration.ts then runs the 7-step safe replacement order.

J. No RS credentials or internal identifiers reach the browser. The Edge Function loads X-REVIEWSTUDIO-EMAIL and X-REVIEWSTUDIO-TOKEN from server-side secrets and uses them only in the Edge Function runtime. Upload responses contain only success/operation and an optional boolean cleanup status; the protected loader returns the public ReviewStudio file URL used by the UI. No X-REVIEWSTUDIO-* header or ReviewStudio project/review/file identifier is returned.

K. Safe replacement order. The orchestrator runs: (1) resolve current persisted row → (2) upload new file to Supabase temp storage + get signed URL → (3) POST new file into SAME Review → (4) verify RS accepted (status 2xx, non-empty review_file.id) → (5) persist the new book_files row staged with is_latest=false → (6) atomically promote NEW and supersede OLD through promote_replacement_book_file → (7) DELETE OLD RS review file. Step 6 is transactional and happens before step 7, so a failed or concurrent promotion never deletes the old ReviewStudio file.

L. Reuse existing proven upload architecture. The replacement path uses the same signed-URL + temp-bucket upload pattern that the first-upload path already uses. The temp bucket is configurable via input.tempBucket. The signed-URL TTL defaults to 3600s and is overridable.

M. 4 failure cases A–D are short-circuited with structured statuses.
A. New RS upload fails (POST returns non-2xx) — old file is untouched, no DB mutation, no DELETE. Returns {ok: false, status: 502}.
B. DB INSERT fails after the new RS file was created — orchestrator attempts to delete the orphan new RS file; the result of that attempt is reported in orphan_cleanup. Returns {ok: false, status: 500}.
C. RS DELETE returns non-2xx (and not 404) — new file is already authoritative; orchestrator reports cleanup_pending in the success result. Returns {ok: true, cleanup_pending: {old_review_file_id, reason}}.
D. RS DELETE returns 404 — old file already gone, treated as success. Returns {ok: true} with no cleanup_pending.

N. No fake cross-system transaction. The brief explicitly forbids unsafe fake transactions across ReviewStudio + Postgres. We do not run them. The new file is fully uploaded to RS, the new book_files row is staged, the database RPC atomically promotes it while superseding the old row, and only then is the old RS file deleted. The loader filter (is_latest = true) exposes only the promoted row; the RS DELETE is treated as a best-effort cleanup with a cleanup_pending flag.

Remaining uncertainty / follow-up

  • The reconciliation job that hard-deletes is_latest=false rows after the RS DELETE is confirmed is out of scope here. Until that job exists, superseded rows accumulate in book_files; the loader ignores them, so the UI is unaffected.
  • The cleanup_pending flag is set in the orchestrator result when the RS DELETE fails. A future reconciliation loop should consume it (or read book_files.is_latest=false rows + a stored metadata.replaces_review_file_id) to retry the DELETE. This task does not implement that loop.
  • No live contract test was performed against iwdnow.reviewstudio.com. The unit + frontend tests are sufficient to demonstrate the local contract but a real RS round-trip is the operator's responsibility.
  • If a future requirement introduces RS file versioning, the loader's explicit is_latest = true contract remains the current-row selector, but the orchestrator would need to stop deleting the old RS file on replacement — instead it would call the versioning endpoint. Out of scope here.
